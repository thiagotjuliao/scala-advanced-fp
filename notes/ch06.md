# Capítulo 06 — Fibers e escalonadores

## Exercício 01 — dois escalonadores atrás de uma interface

| peça | ideia |
| --- | --- |
| `pool(threads)` = `newFixedThreadPool` | `n` threads do SO e uma fila: no máximo `n` tarefas rodam ao mesmo tempo, e uma tarefa bloqueada segura a thread de todas as que estão atrás dela (o deadlock do teste `pool(1)`). |
| `virtual()` = `newVirtualThreadPerTaskExecutor` | Uma thread virtual por tarefa, sem fila; bloqueada, ela sai do carrier e outra roda. Dez mil esperando ao mesmo tempo custam dez mil objetos pequenos no heap. |
| `require` no próprio `pool` | Um tamanho inválido falha na chamada, não no primeiro `execute`. |
| `shutdownNow()`, não `shutdown()` | O `shutdown()` só fecha a porta para tarefas novas: as que estão rodando continuam. O `shutdownNow()` interrompe as threads ocupadas — um pedido, não uma ordem: quem ignora a interrupção continua. Devolve as tarefas da fila que nunca rodaram (`val _ =`). |
| `Thread.ofPlatform().daemon().factory()` | A fábrica padrão cria threads **non-daemon**, e a JVM só sai quando todas as non-daemon terminam: uma pool esquecida e parada segura o programa aberto. Daemon não segura. Threads virtuais são sempre daemon. |
| `Scheduler.from(es)` | Os dois escalonadores só diferem no `ExecutorService`; o resto existe uma vez, no companheiro. |

Onde travei:

- Os 12 testes passaram de primeira, mas o contrato tinha duas promessas que a
  spec não confere: parar tarefas que nunca terminam (`shutdownNow`) e não
  segurar a JVM (threads daemon).
- Não sabia o que era thread daemon.

## Exercício 02 — um loop que termina num `Outcome` e para nos pontos de cancelamento

| peça | ideia |
| --- | --- |
| `Outcome` no lugar de `Either` | Cancelamento não é erro: é o terceiro desfecho. Se fosse um `Left`, um `handleErrorWith` poderia "se recuperar" de um pedido de parada. |
| pontos de cancelamento | Só onde o loop está prestes a rodar código que o programa descreveu: um valor encontrando um `Bind` (antes de aplicar `f`) e um erro encontrando um `Handler` (antes de rodar `h`). Empilhar não roda nada, e um efeito rodando nunca é interrompido. |
| checar no aplicar, não no empilhar | Num `a.flatMap(f).flatMap(g)` todos os `FlatMap` são empilhados antes do primeiro efeito rodar; uma checagem ali nunca vê um cancel pedido no meio. |
| frames com forma (`enum Stack`) | No cap. 05 o frame era um closure `Either => IO`, opaco: o loop não sabia se era bind ou handler, e um closure só pode devolver `IO` — não há `IO` que signifique "cancelado". A decisão tem que estar no loop, e o loop precisa ver o tipo do frame. |
| `Bind[X, E, A](f: X => IO[E], stack: Stack[E, A])` | O tipo intermediário `E` encadeia os nós como os `flatMap` encadeiam: a saída de um é a entrada do próximo. |
| `Handler[X, A](h: Throwable => IO[X], stack: Stack[X, A])` | O valor atravessa sem mudar, então o resto recebe `X`, e `h` tem que produzir `X` também. |
| `Empty[A]() extends Stack[A, A]` | Pilha vazia: o que entra é o resultado. Com isso o compilador deduz `X <: A` no `Succeeded(a)` — sem nenhum cast, ao contrário do cap. 05. |
| `RaiseError(error)` novo no `Bind` | O resto é um `Stack[E, A]` e o `io: IO[X]` não encaixa; um `RaiseError` é `IO[Nothing]` e encaixa em qualquer pilha. |
| `guard` nos três lugares | Função, handler e thunk — o código do usuário que pode lançar. |

Onde travei:

- Apontei primeiro as linhas onde o frame é **empilhado**, não onde é **aplicado**.
- Os tipos do `Handler`: primeiro dei a ele um `E` próprio, depois achei que `E <: X`; o
  certo é `X <: E`, e o caso mais simples é `E = X`.
- Quirk de `enum`: um `case` sem parâmetros de tipo próprios herda a variância do
  `enum`, e o compilador recusa `X` contravariante em posição covariante
  (`contravariant type X occurs in covariant position in type Throwable => IO[X] of value h`).
  Declarando `case Handler[X, A](...)`, o caso é uma classe invariante própria e compila.

11 de 11 testes passando de primeira.

## Exercício 03 — `joinValue` e `both`

| peça | ideia |
| --- | --- |
| `joinValue` = `join.flatMap` nos três casos | Dobra o `Outcome` de volta num programa: valor vira `pure`, erro vira `raiseError`, e `Canceled` vira uma falha `FiberCanceled` — quem esperou não foi cancelado, tem que seguir ou falhar, e não dá para inventar um `A`. |
| `start` dos dois antes de qualquer `join` | É isso que faz rodarem ao mesmo tempo; dar `start` no `b` depois do `join` do `a` roda um depois do outro (o teste do `meeting`). |
| esperar só `a`, e decidir pelos casos de `oa` | Esperar `a` **e** `b` antes de decidir trava para sempre quando `b` nunca termina — e o cancelamento de `b` nunca chega a rodar. |
| `fb.cancel.flatMap(_ => IO.raiseError(e))` | `fb.cancel` solto numa linha só **constrói** a descrição de um cancelamento e a joga fora: o `IO` é descrição (cap. 05). Tem que ser encadeado. O `cancel` espera `b` parar de fato (`requestCancel` e depois `join`). |
| `fb.joinValue` no caso de sucesso | Reaproveita a primeira metade do exercício: o erro ou cancelamento de `b` sobe sozinho. |

Onde travei:

- Primeira versão dava `join` nos dois antes do `match`: timeout de 10 s no teste em que
  `a` falha e `b` é o `spin` infinito.
- O `fb.cancel` estava solto numa linha, descartado. Na saída do teste aparecia como
  `InterruptedException` do `spin` órfão, só parado quando a suíte desligou o escalonador.

18 de 18 depois da correção, nos dois escalonadores.

Limite que fica: este `both` espera `a` primeiro, então se `a` demora um minuto e `b`
falha na hora, o `both` só falha depois de um minuto. Falhar assim que qualquer um falhar
precisa esperar quem termina primeiro — o `racePair` do exercício 04.

## Exercício 04 — `race` e `timeout`

| peça | ideia |
| --- | --- |
| `racePair` | Faz a parte difícil: dois fibers, uma decisão sobre quem terminou primeiro, sem segurar thread esperando. Devolve o `Outcome` do primeiro e o **fiber** do outro, ainda rodando — o que fazer com ele é decisão de quem chamou. |
| `loser.cancel` antes de produzir o resultado | Uma corrida que só devolve o vencedor parou de *esperar* o perdedor, mas ele continua *fazendo* o que faria (o "too late" do teste). O `cancel` espera o perdedor parar. |
| vencedor que falhou ainda é vencedor | A corrida falha com o erro dele, cancelando o outro — esperar o outro transformaria "falha rápido" em "falha quando o mais lento acabar". É o que resolve o limite do `both`. |
| vencedor `Canceled` → `loser.joinValue` | Ninguém na corrida o cancelou, então foi alguém de fora: quem decide é o que continua rodando. Transformar isso em falha faria o cancel de um lado derrubar os dois. |
| `timeout` = `race(io, IO.sleep(d))` | O programa ganha com valor ou erro; o relógio ganha com `TimeoutException`. Como o `race` cancela o perdedor, o programa lento é **parado**, não só abandonado. |

Onde travei:

- Primeira versão tratava o vencedor `Canceled` como os outros casos: cancelava o perdedor e
  falhava com `FiberCanceled`. Passou nos 20 testes — a spec não confere esse caso. Lendo o
  `IO.scala`, ele nem é alcançável hoje: o fiber criado pelo `racePair` não sai dele antes da
  decisão, e o cancel de quem roda a corrida não se propaga aos filhos. O enunciado pede o
  comportamento para quando for.
